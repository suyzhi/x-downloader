# X-Downloader

输入 X（Twitter）推文链接，自动提取其中的 **视频 / GIF / 图片 / 音频**。
视频画质可以手动逐档挑选。

无需登录、无需 API key、无需 Cookie。

---

## 快速开始

把推文链接交给它就行：

```bat
:: 网页版（推荐，双击即可）
启动网页版.bat

:: 命令行版
启动命令行版.bat
```

> 若双击没反应，先看下面的「双击 .bat 没反应」一节。

命令行也可以直接带参数用：

```bat
node cli.js https://x.com/user/status/1234567890
node cli.js https://x.com/user/status/1234567890 -q 720
node cli.js https://x.com/user/status/1234567890 --gif medium
node cli.js https://x.com/user/status/1234567890 --audio mp3
node cli.js https://x.com/user/status/1234567890 -l
```

## 网页版

```bat
node server.js
```

浏览器打开终端里打印的地址（默认 <http://127.0.0.1:8788>）。
端口被占用时会自动往后顺延，并在终端告诉你实际地址。

界面里能做的事：

- 粘贴链接 → 点「解析」，列出这条推文里的全部媒体
- 每个媒体单独勾选是否下载
- **画质逐档单选**，每档显示分辨率与码率，最高档已默认选中
- 转换方式可选：保持原格式 / 转 GIF（5 档预设）/ 只要音频（m4a、mp3、wav）
- 自定义输出目录
- 实时进度条与日志，完成后列出每个文件的完整路径与体积

服务只监听 `127.0.0.1`，不对外网暴露。

## 命令行选项

| 选项 | 说明 |
|---|---|
| `-o, --out <目录>` | 输出目录，默认 `./downloads` |
| `-q, --quality <档>` | 画质。可填 `最高` / `1080` / `720` / `480` / `320`，或列表里的序号 |
| `--gif [预设]` | 转成 GIF。预设：`small` `medium` `large` `original` `max` |
| `--audio [格式]` | 只提取音频。格式：`m4a` `mp3` `wav` `opus` |
| `--all` | 下载全部媒体（默认也是全部，但每项取最高画质） |
| `-l, --list` | 只列出媒体与画质，不下载 |
| `-y, --yes` | 不询问，直接用默认值 |
| `-h, --help` | 帮助 |

不带任何参数运行 `node cli.js` 会进入交互模式，可以连续处理多条推文。

### GIF 预设对照

| 预设 | 宽度 | 帧率 | 适用 |
|---|---|---|---|
| `small` | 320px | 10fps | 微信/聊天发送 |
| `medium` | 480px | 12fps | 通用（默认） |
| `large` | 540px | 15fps | 网页内嵌 |
| `original` | 原始宽度 | 15fps | 保清晰度 |
| `max` | 原始宽度 | 原帧率 | 最高质量，体积最大 |

GIF 采用**两遍调色板法**（`palettegen` + `paletteuse`），比 ffmpeg 默认的单遍输出色带和噪点明显更少。

## 工作原理

X 的推文页在服务端渲染时，会把这条推文的完整媒体信息以序列化数据的形式内联进 HTML
（含 `media_entities` 与 `video_info.variants`）。本工具：

1. 抓取推文页 HTML（`x.com` → `twitter.com` → `mobile.x.com` 依次回退）
2. 解析内联的 `$R[n]=` 序列化数据，按**括号配平**精确切分每段，并解开 `__ref` / `__refs` 引用
3. 用数据里的 `__id` 归属字段（base64 解出的 `Tweet:<id>`）**只取目标推文**的媒体，
   避免把页面里「引用的推文」「相关推文」的图片误当成正文媒体
4. 对视频读取 **HLS master playlist**，拿到权威的画质档位与真实分辨率，再对齐到 mp4 直链
5. 下载到本地

### 为什么画质档位值得单独处理

X 给的 mp4 直链本身不带分辨率信息，只能从 URL 里的路径（如 `/avc1/1080x1920/`）反推，
而且不同推文档位数量不同（有的只有 2 档，有的 5 档）。
HLS master playlist 里写着 `RESOLUTION` 和 `BANDWIDTH`，是最可靠的来源，
所以工具优先解析它，再把每个档位映射回对应的 mp4 直链。

## 性能

解析一条推文页（约 200KB HTML）的主要开销如下：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 页面解析（`extractFromHtml`） | 36.0 ms | **5.3 ms** |
| 网络抓取 | ~2800 ms | ~2800 ms |

页面解析快了约 **6.8 倍**。网络耗时占绝对主导，所以本地这部分的优化对
单条推文的总等待时间影响不大；但在批量处理时会明显体现出来。

做了这几件事：

1. **求值结果记忆化**。X 的页面数据是图结构：一个 `$R[n]` 定义会被父对象、
   兄弟对象和多处列表反复引用。原先每次引用都要重新求值并展开整棵子树——
   实测 476 个定义会触发 **12000+ 次求值、58000+ 次对象展开**，约 25 倍冗余。
   加缓存后每个定义只算一次。

2. **求值函数预编译缓存**。`new Function` 的编译开销远大于执行开销，
   同一段字面量在整页里只应编译一次。

3. **兜底扫描合并为单遍**。原先在几处分别调用三个刮取函数，每个都完整
   扫一遍 200KB 的 HTML，同一段文本被走 7 次。现在合并成一次遍历。

4. **定义粗筛**。页面里 476 个定义中只有个位数与媒体/正文相关，
   先用原始文本特征粗筛，再决定要不要真正求值展开。

5. **去重改用 Set**。原来对每个候选都线性扫一遍已收集项（O(n·m)），
   改为预先构建 URL Set（O(n+m)）。

6. 顺带清掉了 `grab()` 里一段算了两遍、第一次结果直接被丢弃的死代码。

正确性通过对比优化前后 4 条真实推文的完整解析输出验证：媒体数量、类型、
分辨率、时长、画质档位、正文全部逐字一致。

## 常见问题

**双击 .bat 没反应 / 窗口一闪而过**

已修复。此前两个 `.bat` 是 **LF 换行 + 无 BOM** 的 UTF-8 文件，而 `cmd.exe`
解析批处理时依赖 CRLF；LF 会让它逐行错位，报出一串
`'0"' is not recognized...` 之类的错误然后立刻退出，看起来就是「没反应」。

现已改为 **CRLF 换行 + 纯 ASCII 内容**（中文提示改由 Node 输出），
不再受控制台代码页影响。

如果仍然一闪而过，按住 `Shift` 右键该文件 → 「在此处打开 PowerShell 窗口」，
然后手动运行 `node server.js`，就能看到真实的报错信息。

**解析失败 / 提示 HTTP 404**
推文可能已删除、账号已转私密，或链接里的 ID 不对。可以先在浏览器打开确认。

**某个视频提示「该画质只有 HLS 流」**
极少数推文只提供 HLS 变体而无 mp4 直链，这种情况工具会明确跳过而不是下一个坏文件。

**GIF 体积很大**
GIF 格式本身每帧最多 256 色且不做帧间压缩，体积偏大是它的固有限制。
若要更小的文件，用 `small` 预设，或改用 WebP / MP4（同样体积下质量好得多）。

**端口被占用**
服务会自动往后找可用端口，实际地址以终端打印为准。
也可手动指定：`set PORT=9000 && node server.js`
